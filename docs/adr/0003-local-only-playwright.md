# Local Playwright only — no remote browser provider

The browser-driven fallback in `src/core/browser.ts` launches a local Chromium via `playwright-extra` + the stealth plugin. Remote browser providers (Browserbase, Steel, Bright Data, etc.) were considered and deliberately not adopted. The policy is **local only**: there is no `BrowserManager` interface, no adapter seam, no `getBrowserManager()` indirection — `fetchWithBrowser` and `closeBrowser` are exported directly and the singleton Chromium is a file-scoped variable inside `browser.ts`.

The two load-bearing reasons are **cost** and **external dependency**. Remote browsers bill per request or per minute — for an end-user CLI / MCP server fetching a handful of pages, that turns a free tool into one with a recurring SaaS bill, including for users who never trigger the Playwright path. And piping the Playwright fallback through a third party means a vendor outage breaks arcfetch even when the user's machine and target site are both fine; for a tool whose whole job is "fetch this URL", that's a worse failure mode than just running locally.

If a remote provider is ever added it will be a rewrite, not a slot-in. The previous version of this ADR retained a `BrowserManager` interface "so a future remote implementation could slot in cleanly" — that framing was a hypothetical seam with one adapter and a policy forbidding the second, and has been removed. Any future remote path should be opt-in via config and not share a polymorphic type with the local one; the local path stays the baseline that has to work standalone.
